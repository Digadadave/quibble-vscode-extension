# CLAUDE.md — vscode-commit-review

## Project Overview
VS Code extension for reviewing local git commits with GitHub-style inline comments.
The extension stores review data in VS Code's `globalState` (keyed by repo path).

## Architecture
- **`src/extension.ts`** — activation, command registration, repo switching, wiring
- **`src/ReviewPanel.ts`** — sidebar WebviewView: branches list
- **`src/CommentsView.ts`** — sidebar TreeDataProvider: comments list
- **`src/DiffPanel.ts`** — editor WebviewPanel: diff view + inline comments
- **`src/ChangesView.ts`** — sidebar WebviewView: changed files list
- **`src/CommentManager.ts`** — CRUD for globalState comment DB
- **`src/GitService.ts`** — git log, diff, branch listing (shell-exec wrapper)
- **`src/ReviewTreeProvider.ts`** — VS Code TreeView: branches > commits > files
- **`src/icons.ts`** — single source of truth for all icons, colors, and CSS vars
- **`media/sidebar.js`** — webview JS for ReviewPanel
- **`media/comments.js`** — webview JS for CommentsView (if present)
- **`media/review.js`** — webview JS for DiffPanel
- **`media/review.css`** — shared CSS for all webviews

## Constants and Icons — Critical Rules

### `src/icons.ts` is the single source of truth
- **All codicon IDs** → `ICONS` object (e.g. `ICONS.CHECK`, `ICONS.COMMENT_UNRESOLVED`)
- **All SVG filenames** → `ICON_FILES` object (e.g. `ICON_FILES.STATUS_OPEN`)
- **All status colors** → `STATUS_COLORS` object with `token`, `fallback`, `bgFallback`
- **CSS variable injection** → `buildStatusCssVars()` — inject into every webview HTML

Never hardcode codicon strings, color hex values, or SVG filenames elsewhere. Always import from `icons.ts`.

### SVG status icons (`media/icon-status-*.svg`)
Each status has a paired SVG icon file. SVG icon colors must use the **same `fallback` hex** defined in `STATUS_COLORS` for that status. When adding or changing a status color, update both `STATUS_COLORS` in `icons.ts` AND the corresponding SVG fill color.

Current status → color mapping (from `STATUS_COLORS`):
| Status     | Color      | Hex       |
|------------|------------|-----------|
| open       | blue       | `#6c9bcf` |
| question   | coral      | `#c08060` |
| replied    | purple     | `#a78bca` |
| addressed  | green      | `#73a66c` |

### CSS variables
- `--status-{name}` and `--status-{name}-bg` are runtime-generated by `buildStatusCssVars()`
- Do **not** hardcode `--status-*` values in `review.css` — they are injected at runtime
- All other theme colors in CSS use `var(--vscode-*)` tokens with hex fallbacks

## Comment Status Model
`CommentStatus = 'open' | 'in-progress' | 'needs-input' | 'addressed' | 'approved' | 'resolved' | 'dismissed' | 'outdated'`

The `STATUS_META` record in `CommentsView.ts` maps each status to a `{ label, icon, color }`.
The `FILTER_GROUPS` array groups related statuses for the multi-select filter picker.
When adding a new status, update both `STATUS_META` and `FILTER_GROUPS`.

## Data Flow
1. Sidebar (branches) → user clicks branch → `branchSelected` msg → extension
2. Extension → loads commits → `DiffPanel.setBranchCommits(branch, commits)`
3. DiffPanel commit picker → user selects → `selectionChanged` msg → `DiffPanel.ts`
4. DiffPanel.ts computes diff, sends `diffResult` to webview, fires `onSelectionChanged`
5. Extension `onSelectionChanged` → `CommentsView.updateComments(comments, hashes)`

## Mutation / Refresh Pattern
- `CommentManager.save()` must **not** fire `_onDidChange.fire()` — that event is for external/agent file changes only (via file watcher)
- Internal mutations are handled by the `onCommentMutation` callback in DiffPanel
- Avoid double-refresh bugs: only one code path should trigger a UI refresh per user action

## Webview Conventions
- All webview JS files use `// @ts-check` and `/// <reference lib="dom" />`
- Message passing: webview → extension via `vscode.postMessage({ type, ...payload })`
- Extension → webview via `panel.webview.postMessage({ type, ...payload })`
- Event delegation: use `data-action` attributes + a top-level `document.addEventListener('click', ...)` rather than per-element listeners
- State is kept in a single `state` object at the top of each webview JS file

## Code Style
- Prefer `const` over `let`; avoid `var`
- Use section dividers: `// ── Section name ──────────...`
- TypeScript: strict types, `as const` on literal objects, prefer interfaces over type aliases for shapes
- No over-engineering: minimal abstractions, no helpers for one-time operations
- Keep changes focused — don't refactor surrounding code when fixing a bug
